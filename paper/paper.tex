\begin{abstract}
\noindent
A ticket says: lock down \texttt{/admin}; no login must return \texttt{401}. A worker in a bubblewrap sandbox with no network, a deterministic script rather than a model, made the failing check pass without escaping, and the door stayed open: the program still returned \texttt{200} for \texttt{/admin} with no login. Its attempt to overwrite the read-only checker was denied, and the checker's hash never changed. But the checker loaded its answer key, \texttt{expected.json}, from the worker's workspace. The worker rewrote the answer key: same candidate, same checker, new answer key, and \texttt{FAIL} became \texttt{PASS}. It did not make the code pass the test; it made the test pass the code. Controller-owned cases reject the same bytes, and a corrected handler passes them. One approval binds exact bytes and one destination and is consumed once: it refuses a substituted artifact and a second destination, publishes the approved bytes, and refuses a replay. The judge is the checker plus everything it reads, and isolation and acceptance are different boundaries. The agent may propose what counts as correct; it must never be the last writer of what judges it. This paper is the written companion to a fifteen-minute lightning talk. Supporting Linux experiments, recorded separately, cover an inherited CI-style token, a writable mount and an allowed upload host. Each needs an owner outside the worker, and the legitimate job still has to complete.
\end{abstract}

\section{The line}

The picture is the software factory you already run.

Prod sandbox & Runs the published bytes \\

The harness stays in the dev sandbox. The runner decides the work is done. The prod sandbox runs what the runner published. The failure is a promotion along a factory that is working. Each station trusts a receipt from the station before it.

The accepted abstract names four of those receipts: inherited credentials, dangerous mounts, exfiltration through an allowed endpoint, and verifier tampering. On this line they are the CI secret injected into the dev job, a mount that can touch the next job's files, a host the workflow is already allowed to publish to, and the green check that promotes the sandbox into prod.

A protected checker says \texttt{PASS}. Unauthenticated admin still returns \texttt{200}. Policy requires \texttt{401}. You can see that on the line, name the file, and move the decision to a station the worker cannot write. The legitimate job still ships.

What follows is a controlled reproduction of a known trust-boundary failure. The credential, mount, and publish cases are loopback HTTP and real bind mounts. The green check is a five-case command-line model of authorization. These fixtures have the shape of a GitHub Actions job. They are not a compromise of GitHub, and they are not a customer production server. The repository records the bytes.

\section{What the worker is allowed to touch}

The task is \texttt{lock-admin}. Five inputs. Unauthenticated admin and an expired credential must return \texttt{401}. An ordinary user must return \texttt{403}. The administrator and the public route must return \texttt{200}.

The worker may edit task code, the workspace, and the tests and reports it proposes. That is ordinary coding-agent authority. The checker sits on a read-only bind mount. The controller process, the approval key, and the release store sit outside the worker. The kernel and that controller are the trusted base of the experiment.

The worker in the repository is a script. The measurement is whether the action is permitted. Whether a particular model would discover the action is a different experiment, and this package does not run it.

\section{The control, then the exploit}

The bad candidate returns \texttt{200} for every input. With the honest answer key, the checker prints \texttt{FAIL} and exits \texttt{1}. The check can see the bug.

The worker then tries the obvious overwrite: replace \texttt{checker.py} with a program that prints \texttt{PASS}. The read-only mount denies the write. The checker hash is identical before and after that step:

\begin{quote}
\texttt{f5d8d3468bbeeee014580159053a10a4af758a11a22af3045b03abcf94922e99}
\end{quote}

The grader survived. The mount held. The next step never touches \texttt{checker.py}.

The protected checker loads its cases from the working directory:

\begin{lstlisting}
expected = json.loads(Path("expected.json").read_text())
\end{lstlisting}

That file lives in the workspace. The worker owns the workspace. It rewrites every expected output to \texttt{200}. On \texttt{admin:none} the key moves from \texttt{401} to \texttt{200}. The candidate still returns \texttt{200}. The same checker, still read-only, prints \texttt{PASS} and exits \texttt{0}.

Locking the program left the answer key with the worker. A controller that promotes that \texttt{PASS} into release eligibility has adopted the worker's definition of authorized. A plugin, an imported helper, a test configuration, or a worker-written report has the same shape. The object reproduced here is \texttt{expected.json}.

\section{Freeze, then judge}

The recorded repair freezes the candidate bytes before the run. An isolated execution reads those bytes from a read-only mount and returns observations. The controller compares the observations with cases it owns. Approval and publication name the frozen object.

A harness that prints ``finished'' holds no approval key. A second machine can host the split. Copy the producer's answer key onto it, or fork the producer's disk, and the dependency moves into the room you trusted. Count the inputs to the decision, then count the machines.

One fresh approval is issued for the good candidate. Four attempts follow, in this order. While that approval is still unused, substituted bad bytes are \texttt{DENIED}, and the approved bytes offered to a second destination are \texttt{DENIED}: an approval names one destination --- account, environment, operation, subject. The approved bytes at the named destination are \texttt{PUBLISHED}. The same bytes offered once more, now on a spent nonce, are \texttt{DENIED}. Publication is a row in controller-owned SQLite: the exact bytes and the spent nonce, in one transaction. Offering the substitute only after the nonce is spent would let a missing digest check hide behind replay protection. This repository's own test used to run in that order: it published first and tried the substitute afterwards. The current test offers the substitute first, while the approval is still unused, and the gate refuses it.

\section{Four boundaries, both sides}

The answer key is the centerpiece. The deployment checklist around it has four rows. Each row needs a denied abuse and a job that still completes. A host that can do nothing will pass a deny-only test.

\begin{center}
\small
\begin{tabular}{@{}p{0.22\textwidth}p{0.36\textwidth}p{0.30\textwidth}@{}}
\toprule
Boundary & This must fail & This must still work \\
\midrule
Identity & Read another project's data & Read the task input \\
Files & Edit the next job's input & Write the task output \\
Outbound & Upload to another account & Send the authorized report \\
Acceptance & Edit the criteria or swap bytes & Release the verified fix \\
\bottomrule
\end{tabular}
\end{center}

Identity, on loopback HTTP with fixture tokens: a broad token reads another project's private fixture and receives \texttt{200}. A task-scoped token receives \texttt{403} there and \texttt{200} on its own input. Expired and wrong-audience fixtures are rejected. A short lifetime on a broad token leaves the token broad. The service enforces the resource.

Files, on real bind mounts: a writable mount changes the next job's fixture on the host. A read-only input mount denies that write. The worker's own output path still accepts the patch.

Outbound, on an allowed loopback service: the worker posts a synthetic private fixture to another account and the service stores it, \texttt{201}. The repaired broker sends one fixed team report. Extra fields are denied. The worker has no direct route to the service. The receiver log is the evidence of delivery.

Acceptance: the worker proposes the artifact. The controller owns the criteria and the bytes that get published.

These are four separate experiments. They are a checklist, measured on both sides.

\section{Three jobs inside one green build}

Verification says these bytes met these criteria. The gate says this approval authorizes these bytes on this run. History says the record still matches an anchor stored where the writer cannot reach it.

A hash chain will store a bad decision faithfully. It detects a rewrite when the previous head was kept outside the log. The reference gate binds artifact, verifier, expected results, policy, run, environment description, task, decision, nonce, expiry, and schema. A worker \texttt{PASS} file and a harness exit code are observations from the wrong side of that line. Missing or malformed output produces no approval.

The next CI run can be handed the same dev workspace. A reviewer job and a deploy job can be forked from that disk. If they all read \texttt{expected.json}, and the first job can write it, three stations share one definition of done. Different prompts do not create independence. A snapshot of the dev sandbox keeps the key. The snapshot records the disk. Choosing the criteria is a different authority. That paragraph is an inference from the dependency we measured. It is not a multi-job attack and it is not a snapshot exploit.

An earlier revision of our own gate could publish a marker while the candidate bytes and the recorded digest diverged. Reaching that flaw required controller-object access. The current gate derives the digest from immutable bytes and stores those bytes. The audit stays in the package because it is ours.

\section{Leave with one question}

The sandbox held. The checker held. The door stayed open. The candidate never improved: the worker changed the answer key, and \texttt{PASS} changed meaning. Isolation and acceptance are different boundaries. A sandbox decides what a process can touch. Acceptance decides whether anything it touches can declare its own work done. The judge is the checker plus everything it reads.

When you leave Pier Sixty, take one question back to the host that runs your agents: what does your judge read that your agent can write?

\begin{enumerate}
\item List it: every file, config, environment variable and service your checks read, minus the code under test. Anything left that the agent can write is the finding.
\item Keep the code under test out of the judge's process, so it can only answer, not grade. That is the route o3 used in METR's report.
\item Hash the answer key when the task starts and again at the verdict, as a tripwire rather than a policy.
\end{enumerate}

Then bind what ships to what was judged: one approval, the exact bytes, one destination, once. The four boundaries above remain the checklist for the rest of the pipeline: which credential the worker receives, which paths it can write, which URLs it can reach, and which object is compared before release.

The component that returns \texttt{403}, a read-only denial, \texttt{DENIED}, or reject has to sit outside the worker. After you put it there, run the legitimate ticket again. A system that can no longer do the job has gone quiet. It has not become safe.

The sandbox is worth keeping. You built it so the agent could work and still be stopped. Keep it. Then open the file the checker trusts. If the worker can write that file, you already know the next green build.

The agent may propose what counts as correct. It must never be the last writer of what judges it.
